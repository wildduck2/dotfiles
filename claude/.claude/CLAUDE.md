# Global instructions

- Keep every reply short and clean: a couple of lines, verdict first, then what changed. Do not restate the work, narrate the steps, or explain reasoning unless asked. One sentence for a real caveat. This applies to chat replies, not to documents I ask you to write.
- Do not use subagents (the Agent tool) unless I explicitly ask for one. Do all research and implementation directly.
- Never add yourself (Claude) as a co-author on git commits. Omit any `Co-Authored-By` trailer.
- Never use em dashes (—) in anything you write: code comments, docs, commit messages, plans, or chat replies. Use a comma, a colon, parentheses, or a plain hyphen instead.
- Keep code comments short and human: one or two lines explaining *why*, matching the density of the surrounding file. No long multi-paragraph blocks that restate what the code does.
- When a plan, milestone or port step is finished, run the full end-to-end suite once and recommend it without being asked. Partial runs taken during the work are measured against artifacts that were still being rebuilt, so they never describe one coherent state. Rebuild every generated artifact first, in dependency order, and do not let anything else build while the suite runs. Report the number from that single run, not an assembly of earlier ones.
- When a repo tracks its tests in a map or parity file (in IRYSS that is `apps/marketplace-api/test-map.json`), update it in the same change that adds, renames or deletes a test, listing the real case names. A test absent from the map is untracked coverage and the totals in it become a claim nobody is checking. When touching that file, verify the counts it states against the files on disk rather than trusting them, since drift is what the file exists to prevent.
- Sweep the same finished work for the rules above before reporting it: no em dashes anywhere, and no AI-slop comments (restating the code, narrating the change or its history, section banners, doc blocks repeating parameter names, hedging notes). Grep for the characters and read the diff's comments rather than assuming, since these accumulate fastest in code written quickly. Fix what the sweep finds instead of listing it.
